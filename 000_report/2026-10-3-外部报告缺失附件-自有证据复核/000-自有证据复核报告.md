## 复现结果

### 一、精度丢失的根因与修复（对应报告第四节、第六节 6.2）

`precision_recheck.json` partA：

- 根因复现：在当前 Wolfram 15.0 上，`Precision[ToExpression["0.0`40"]]` 仍是 `MachinePrecision`
  （`preFixZeroLiteralPrecisionIsMachine = true`）。这正是报告第四节指认的机制——给零字符串套上
  "加小数点、加精度标记"的普通数转换会得到机器精度零。该机制与 Wolfram 版本无关，14.3 与 15.0 一致。
- 修复后解码表（直接调用成品 `FlintNDE`Private`flintNDEDecodeComplex`，40 位），四种输入均未出现
  MachinePrecision（`shippedDecoderAnyMachinePrecision = false`）：

  | 输入 | 实部 Precision | 虚部 Precision | 复数 Precision |
  | --- | --- | --- | --- |
  | 高精度实部 + 零虚部 | 40 | Infinity（精确零） | 40 |
  | 零实部 + 纯虚数 | Infinity | 40 | 40 |
  | 实部虚部均非零 | 40 | 40 | 40 |
  | 实部虚部均为零 | Infinity | Infinity | Infinity（精确零） |

  与报告 6.2 的表逐项吻合。在用修复比报告建议的 `If[mantissa === "0", Return[0]]` 更宽：它按字面识别
  任意全零尾数（含 `0`、`0.0`、`-0` 等），且不设"小于某阈值即当零"的容差，真正非零的小分量仍按 40 位解码。

### 二、独立 Wolfram 接口端到端（对应报告第三节 3.2、3.3）

`precision_recheck.json` partB，用报告 3.1 的同一方程 `A=diag(1/(z-1),-2/(z+3))`、`y(0)={1,1}`、
80 位工作精度 / 40 位输出 / 主 40 参考 48 / 目标 `1e-30`：

- 返回向量 `{0.5`40., 0.7346938775510204081632653061224489795918000000000000000001`40.}`，
  `Precision` 列表为 `{40., 40.}`，`anyComponentMachinePrecision = false`。报告 3.3 记录的修复前值是
  `{MachinePrecision, MachinePrecision}`；当前字节已不再退化。
- 主/参考内部相对差 `[3.3998e-45 +/- 4.79e-86]`，与报告 3.2 的"约 3.40e-45"一致；`targetRelativeErrorMet = true`，
  `certificationMode = certified`。
- 对闭式 `{1/2, 36/49}` 的最大绝对差约 `10^-39.83`（≈1.5e-40），远低于目标 `1e-30`。

### 三、并行 Wolfram 接口（对应报告第五节第 3 条）

`precision_recheck.json` partC，`FlintNDEEvaluateEpBatch` 跑 `y'=ep/(1+x)y`、`y(0)=1`、ep ∈ {1/5,1/6,1/7}：

- 三个 ep 的返回向量 `Precision` 均为 40，`anyReturnedVectorMachinePrecision = false`；输入顺序保持；
  对闭式 `2^ep` 的最大绝对差 `4.11e-41 < 1e-30`。报告第五节第 3 条指认的并行路径返回向量退化，在当前字节已不复现。

### 四、Python 并行示例的通过条件（对应报告第七节）

`ep_parallel_recheck.json`，直接跑开发版独立包 `package-FlintNDE/examples/ep_parallel.py`：

- 阶数已是主 112 / 参考 128，声明目标 `1e-40`。
- 通过条件源码为 `result["target_relative_error_met"] and relative_error < arb(TARGET_RELATIVE_ERROR)`：
  既检查后端自认达标，又把闭式相对差与**同一个声明目标**比较；`hardcodedAbsDiff1e30GatePresent = false`，
  报告第七节指出的"按绝对差 `< 1e-30` 判断通过"的硬编码门禁已不存在。阈值只来自声明的 `TARGET_RELATIVE_ERROR`，
  改目标即改判据，不再检查一个与示例无关的量。
- 三个 ep 的闭式相对差为 2.47e-43 / 2.51e-43 / 2.48e-43，最大 2.51e-43，与报告第七节"改成 112/128 阶后
  最大闭式相对误差约 2.51e-43"一致；`allEpPassed = true`，示例打印 PASSED，退出码 0。

## 不可复现部分及原因

1. **修复前的端到端数值**：报告 3.3 的 `{MachinePrecision, MachinePrecision}` 返回向量与约 `3.85e-17`
   绝对误差，产自修复前的成品仓提交 `da496dd`。当前四份副本都已含修复，无法从当前字节重新生成这组"修复前"数值。
   替代做法是复现其**机制**：`ToExpression["0.0`40"]` 在 15.0 上仍为 MachinePrecision（partA），
   且修复后的解码/接口在四类输入与两条官方路径上都不再退化（partA/partB/partC）。
2. **原环境本身**：报告在 Wolfram 14.3 + Python 3.13.1 + SymPy 1.14.0、另一台机器（`C:/Users/Moons/…`）上运行；
   本复核在 Wolfram 15.0 + Python 3.12.7 上针对当前字节。根因机制与版本无关，但逐位的"修复前"环境未重新实例化。
3. **`closed_forms_vendor.json`（Vendor 副本 Python 示例对照）**：未单独重跑 MadStree v0.17 Vendor 内的
   Python 示例。依据是 Vendor 与开发版独立包的 FlintNDE 字节一致（同为 `6E40F021…`，解码逻辑逐字相同），
   故独立包一侧的闭式对照（`ep_parallel_recheck.json`）覆盖同一算法；这是基于字节同一性的推定，不是对 Vendor 的独立重跑。
4. **九份原附件的具体内容**：均已不在仓库，无法取回；本目录提供的是自有的等价重跑证据，不是对原附件的恢复。

## 结论

外部报告缺失的九份附件无法查阅，但报告的每一条实质结论都能用当前仓库字节独立复核：精度丢失的根因机制
（第四/六节）已复现，修复在四类输入、独立接口、并行接口三条路径上均确认生效（第三/五节），Python 并行示例的
门禁已改为与声明目标同源、无硬编码绝对差阈值（第七节），两处 README 表述已按建议更正（第三节）。唯一无法从当前
字节重新生成的是"修复前"的端到端具体数值——因为修复已落在全部四份副本里；这一缺口以机制级复现替代，并在上节明确标注。
据此，外部报告的结论在自有证据下成立，缺失附件不构成对当前发布字节的未决风险。
