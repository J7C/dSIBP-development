## 4. 已确认发现

### F-01 [中] dSIBP 022 仍实际接受并执行旧运动学 schema

**预期契约**

- 根规则规定当前版本不保留旧字段别名、fallback 或兼容解析分支。
- dSIBP `AGENTS.md` 明确写明 022 只读取 `loopExternalMomenta`、`independentExternalMomenta` 和统一 `kinematicRules`，不读取其它字段名或别名。
- `LoopCore013.wl:85-93` 的正式 key 表也只列 `kinematicRules`。

**实际实现**

- `Kernel/Core/KinematicCoordinates.wl:540-559` 在缺少 `kinematicRules` 时仍依次读取：
  `loopKinematicRules`、`resolvedLoopKinematicRules`、`magnitudeKinematicRules`、`resolvedMagnitudeKinematicRules`，并把来源标为 `legacyFields`。
- `Kernel/Core/LoopCore013.wl:267-278` 虽把这些键放入 `unknownKeys`，但 `inputPreflightPassQ` 只检查缺失必需键和 malformed issues，不检查 unknown keys。
- `parseTopology` 在 `LoopCore013.wl:678-719` 调用上述 parser，并把结果写入正式 topology。

**触发条件与已复现输出**

对一个合法 022 最小 case，不给 `kinematicRules`，只增加：

```wl
"magnitudeKinematicRules" -> {sp[k, k] -> oldSquaredK}
```

一次性探针实际返回：

```text
inputPreflightPassQ -> True
unknownKeys -> {magnitudeKinematicRules}
parseSucceededQ -> True
resolvedMagnitudeKinematicRules -> {sp[k,k] -> oldSquaredK}
```

这不是仅保留旧名字的注释，而是可执行兼容通道。

**直接后果与下游传播**

- 022 调用者可在不知道当前统一 schema 的情况下继续用旧字段改变内部坐标规则。
- `KinematicCoordinates.wl:648-661` 从 `resolvedMagnitudeKinematicRules` 构造公开坐标数据；同一 topology 字段还进入 naming report、数值规则规范化及后续导数/DE/scaling 的坐标解释。
- 结果不一定立即报错，因而属于特定输入下的静默接口越权；正式 022 当前 schema 输入不受影响。

**修复边界**

1. 从 `resolveKinematicRulesForCase` 物理删除四个旧 Lookup 和 `legacyFields` 分支。
2. parser 只从 `kinematicRules` 构造统一 audit；内部 `resolved...` 字段可以作为 producer 输出保留，不得再作为 raw case 输入读取。
3. 不为已删除的 raw-case 名字保留 denylist 或专门错误语义；普通 unknown keys 继续按 022 合同忽略。
4. 保留当前 `kinematicRules`、坐标完备/过完备门禁和 derivative capability 逻辑。

**验收方法**

- 当前 022 输入和 `kinematicRules` 正例继续通过。
- 当前 runtime 与现行测试中不再保存四个旧 raw-case 名字；额外 unknown key 不影响 preflight/parse。
- 当前 `kinematicRules` 的结构和坐标完备性仍由现行输入门禁检查。
- 重跑 `check_022_topology_schema`、运动学 Jacobian/DE/scaling 专项和正式单文件路径检查。

### F-02 [低] dSIBP sector prefactor consumer 保留旧 metadata 重建分支

**预期契约**

当前 producer 与 consumer 应共享唯一的现行 `sectorPrefactorData` schema；缺少结构性主字段时应失败，而不是尝试解释旧 artifact。

**实际实现**

- `Kernel/Core/SectorModel018.wl:371-385` 的当前 producer 每次都生成 `kEPower`。
- `SectorModel018.wl:389-400` 的 consumer 在 `kEPower` 缺失时，仍用 `parameterList` 与 `powerList` 重建 prefactor，并以变量 `legacyQ` 明确标记该路线。
- 当前仓库 producer 无法生成这种缺字段状态，说明它是旧 metadata/artifact 兼容分支，不是当前算法需要。

**触发条件**

只有调用方手工构造、篡改，或把缺少 `kEPower` 的旧 `sectorPrefactorData` 注入当前 context/consumer 时触发。当前正常 `DSInit` 路线不触发，因此严重度为低。

**直接后果与下游传播**

consumer 不拒绝旧结构，而会生成一个看似合法的 prefactor。该函数被 contact normalization、sector ratio/log derivative、DE metadata 和 `DE/Scaling.wl:66-72` 使用；若旧结构被注入，影响会继续进入 relation coefficient、DE/scaling degree。

**修复边界**

- 删除 `legacyQ` 与 `parameterList/powerList` 重建分支；缺 `kEPower` 返回结构化 Failure 或 `$Failed`。
- `parameterKeys/parameterList/powerList` 当前仍写入正式 metadata 和文档，可作为诊断字段保留；不要把“删除 fallback”误做成未经迁移就删除全部 metadata 字段。
- 保留 `kEPower`、`kEParameterExpressions`、`residualPowerParts` 和 `constantPrefactor` 的现行物理组合。

**验收方法**

- 当前 producer 生成的数据 materialize 结果保持 exact 相等。
- 对当前数据执行 `KeyDrop[data,"kEPower"]` 后必须 fail closed，不能返回 prefactor。
- contact ratio、DE scaling、time-only/full-loop 相关现行回归继续通过。

### F-03 [低] MadStree 正式 Kernel 加载已退休的单顶点 Frobenius 特殊路线

**预期契约**

当前版本生产 Kernel 不保留已被 generic sector-DAG 路线替代的旧实现；若独立 oracle 仍有价值，应放在测试所有权下且有真实消费者。

**实际实现**

- `Kernel/Numerics/Boundary.wl:335-337` 明写该特殊路线在 v0.10 已退出 production。
- `Boundary.wl:885-891` 的 `MSBoundaryData` 对所有边界只调用 `msGenericSectorFrobeniusData`。
- 但 `Boundary.wl:275-463` 仍加载 4 个封闭定义：
  `msMultiIndices`、`msPaperFTilde4`、`msVertexFrobeniusComponent`、`msSingleVertexFrobeniusData`，共 189 个物理行。
- 注释声称 tests 用它比较 generic route；全仓精确搜索显示这四个名字只在该封闭块内部出现，没有任何 test/validation consumer。

**触发条件、直接后果和传播**

加载 `Boundary.wl` 即定义这些符号，但当前生产入口不会调用。它不改变当前数值结果；后果是正式 Kernel 永久携带一套已退休公式、注释形成错误证据，并在未来修改 endpoint convention 时产生双实现漂移风险。下游当前无传播。

**修复边界**

- 删除上述 4 个定义和两处“仍作为 oracle”的失实注释。
- **不得删除** `msPaperC` 和 `msVertexEndpointCoefficient`：generic 路线仍在 `Boundary.wl:682-696` 使用后者。
- 若确实要恢复论文公式 oracle，应在 test/独立验证目录重新建立来源隔离的 oracle 和实际断言，而不是把未调用代码塞回 Kernel。

**验收方法**

- 全仓搜索四个退休符号为零，加载后无相应 DownValues。
- `check_core.wls` 仍为 `58/58`；重跑 boundary、massive/massless edge 和当前独立 validation case。
- 对 generic boundary 的 endpoint coefficient、anchor、finite-part 结果做 exact/numerical identity，不以“旧函数已删除”代替行为验证。

## 5. 排除项：不是死代码或兼容层

以下命中经过调用链复核，不应在清理时误删：

1. **dSIBP 的 013/016/018/020 后缀符号**：当前 022 Kernel 中仍有大量这类 identifier，它们多数有真实 caller，是滚动架构命名债务，不是仅凭后缀即可删除的旧实现。
2. **`makeAtomicExternalInvariantDerivativeDecomposition` 的 DownValues 复制**：`KinematicCoordinates.wl:790-827` 是当前 Jacobian wrapper 的实现方式，不是兼容入口；但属于脆弱的补丁式分层，见优化建议。
3. **MadStree 的 `massiveFull/massiveCross/...`**：它们是由当前 `vertexType` 和公开 `massive/massless` 输入派生的内部类型，不是旧公开 line-type parser。
4. **`msVertexEndpointCoefficient`**：generic boundary 正在调用，不能随退休 special route 一并删除。
5. **MadStree vendor FlintNDE**：依赖方向为 `MadStree -> FlintNDE`，当前是受控 vendoring，不是可直接删除的普通重复目录。
6. **零内部引用的 documented direct-module API**：`regular_point_de` 等模块允许直接导入；在没有明确替代合同前，不能只凭仓库内部调用计数删除公开函数。

## 6. 其它优化建议

按优先级建议如下。

### O-01 让 schema 白名单成为单一执行源

dSIBP 当前 `optionalCaseInputKeys` 只用于报告，parser 另行 Lookup 字段，导致 F-01。应让 parser 从同一 schema 对象取值，并让 unknown-key policy 在一个入口执行。MadStree 当前也有“额外键一律忽略”的设计；若按本次用户要求追求严格干净接口，建议三包统一为：公开 Association/JSON 的未知键 fail closed，扩展只通过明确命名空间或 options。

### O-02 增加“无兼容残留”静态门禁

- Wolfram：维护退休符号/字段 denylist，检查源码定义、DownValues 和 raw parser Lookup；不要只检查重复 DownValues。
- Python：在 unittest 前运行 AST unused-private scan；公开 API 以 `__all__` 或显式 manifest 为准。
- 门禁应区分“旧名字只出现在 UPDATE_NOTES/拒绝测试”与“旧名字仍被 parser/loader 执行”。

### O-03 把 FlintNDE vendor 同步做成单源机械步骤

建立 canonical-to-vendor 同步/check 脚本：代码和配置要求同 SHA-256，README 只允许明确的相对路径差异。这样删除 F-05 后不会漏掉 vendor，也避免未来两份手工修改。

### O-04 删除 dSIBP 的运行时 DownValues 改写

`KinematicCoordinates.wl:793-827` 先复制旧函数 DownValues、Clear 原名、再包 Jacobian。建议在原定义处直接提取一个明确的 atomic helper，wrapper 正常调用 helper；这能消除加载顺序和 pattern 替换脆弱性。该项是结构优化，不应与删除 F-01 混成一次大改。

### O-05 最后再处理版本后缀命名债务

在功能性兼容层和死代码清理、测试稳定后，再机械重命名仍有真实 caller 的 `...013/...016/...018/...020` 内部符号。收益是降低“当前实现还是历史实现”的阅读成本；风险是纯改名 diff 很大，因此应单独提交并以模块 ownership/DownValues/全回归验收。
