## 1. 补充范围

本轮逐条复核最新版 benchmark 第 14.3、15.1、15.2 和第 16 节，只补做此前 `tree 22/22` 没有覆盖的两路线验证。冻结的 `codex-independent-benchmark/tree/expected.wl`、全部 `derivation.md` 和两份 frozen manifest 均为只读输入；没有依据 package actual 改写手推结果。

要求的两条路线为：

1. 从 `DSTreeSeeds` 返回的完整 local binary block 线性方程，独立用系数矩阵求解 general `A-/A+` 和指定终点约化；
2. 调用 package 的直接公式迭代接口 `repIterative0`/`repIterative`，并将直接 `DSTreeDLogDE` 与 seed-derived recurrence 组装的 DE 逐项比较。

## 2. 已确认的中间结果

- 两顶点 `G++` 的 general seed 方程可直接抽出 `A-=-C_{a-1}^{-1}C_a` 与 `A+=-C_a^{-1}C_{a-1}`；两矩阵均与冻结直接公式逐项相等。
- source-aware 同号 contact 一步约化中，seed 方程路线与 `repIterative` 的符号差值为零。
- 三顶点 `G+-` 端点的两级约化中，seed 方程路线与 `repIterative` 的符号差值为零。

以上只说明 `repIterative` 返回值可与 seed 方程对齐，尚不能替代对公开 `repIterative0` 的合同检查。

## 3. 新发现的不符合

### N4. `repIterative0` 未由公开 tree 调用路径初始化

最小复现是在新 kernel 加载 `package_014.wl`，完成 `DSInit`，随后调用两顶点和三顶点的 `repIterative[expr,end,context]`；调用后：

```mathematica
InputForm[repIterative0]
(* {} *)
```

源码中 `setTreeFamilyContext[data]` 会设置 `$dSIBPTreeFamilyContext` 和 `repIterative0=makeRepIterative0[data]`，但当前单文件 package 只有该函数定义，没有任何调用点。公开 `repIterative` 的显式 context 重载直接进入 `repIterativeData`/`repIterativeSectorData`，因此不会更新 `repIterative0`。

责任判定：不是手推错误，也不是 frozen expected 的 convention 问题；这是 package 公开接口实现缺陷，同时也是此前 tree checker 的漏检。`repIterative` 主返回值仍可工作，但任务书第 14.2--14.3 节要求单独调用并比较 `repIterative0`，且用户手册/`::usage` 声称它保存最近一次 tree 单步原始规则，当前行为不符合该合同。

## 4. 修正与重跑门禁

- 修正公开 `repIterative` 调用路径，使显式 tree data/context 调用同步设置当前 tree family 和 `repIterative0`；sector context 必须保持 sector identity，不能退回裸 `J` 猜 sector。
- 新 checker 必须加入 general `A-/A+`、source-aware 终点约化、确定性有理 probe、seed-derived DE 和 `repIterative0` 非空/实际改写断言。
- 修正后重新构建 `package_014.wl`，清空全部 package-facing results，重跑七组检查并复核 frozen hashes。
